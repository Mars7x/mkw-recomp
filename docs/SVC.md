# Explicit service transport

CPU-v10 now has an opt-in service-table-v3 profile. It adds typed SVC dispatch, transactional memory/multiple-register replies and a terminal thread-exit signal over the existing coherent memory/call authority. CPU frame layout, ABI v9 and native table-v1/v2 headers remain unchanged. This is transport, not a Horizon service implementation or permission to execute original code.

## Why this boundary

Private static inspection finds 79 indexed SVC wrappers with 72 distinct immediates; every complete wrapper contains one SVC. The supplied CreateThread wrapper consumes W1 after the SVC; CreateEvent consumes W1 and W2. Filesystem HLE's U32 return changes only X0 and cannot substitute for this kernel interface. Keeping SDK initialization code where feasible avoids guessing entire SDK thread-object layouts. The exact exported GetCurrentThread getter corroborates a current-thread pointer at TLR offset 0x1f8 in this SDK, but does not establish full TLR/thread-object sizes, TLS templates, or retail startup configuration. Input-derived wrapper code/details remain private.

## Contract

- Only `decode/lift_*services_v3` accepts SVC; legacy/default/v10 decoders still refuse it. All 65,536 immediate encodings are tested, with exception-instruction neighbors kept separate. CFG, bounds, tail and object-size rules are unchanged. Legacy emitters reject manually supplied SVC IR.
- The explicit v3 table has nested-call and SVC callbacks with one attested context. Query checks distinguish CPU frame version 10 and table version 3 before target function lookup. Mixed native profiles reject; v2 and v3 entries/attachments refuse each other. Native callees must be compiled/registered for the same profile. ABI9 prefix call fields remain empty.
- SVC consumes one guest instruction before dispatch. Host service work does not fabricate guest instruction counts. Calls share budgets/module-base restoration and bounded depth. A normal reply continues at the next label; a terminal reply propagates status 9 through nested callers without running their continuations. This signal alone does not implement Horizon ExitThread lifecycle.
- The registry contains only explicitly registered u16 numbers, rejects duplicates and has a 256-handler quota. Unknown handlers, out-of-range FFI numbers and foreign frames/contexts refuse. There are **no built-in Horizon handlers or successful generic stubs**.
- A service gets a snapshot of X0–X7 and checked, bounded guest reads/output validation, without mutable CPU/context pointers or recursive dispatch. Replies can set X0–X7 using explicit W zero-extension or full X values. Duplicate/out-of-range register writes refuse. Other GPRs, SP, flags, vectors and software thread-register state remain unchanged by the transport.
- Memory replies contain at most 32 writes / 1 MiB. All ranges validate before any packet memory/register output commits, under the same owned authority. Same-value writes invalidate overlapping reservations. On handled completion the caller's local reservation clears, including empty replies; peers remain reserved unless overlapping memory writes invalidate them. Unknown/refused/faulting packets preserve pending reservations and all packet outputs. Prior instructions/external handler effects are not rolled back.
- The exception-return monitor rule is corroborated by [QEMU 8.2.2 AArch64 user-mode source](https://github.com/qemu/qemu/blob/11aa0b1ff115b86160c4d37e7c37e6a6b13b77ea/linux-user/aarch64/cpu_loop.c) and synthetic native/QEMU probes. QEMU implementation source is retained privately as reference; no GPL implementation code was copied. This remains software evidence, not verification of all target kernel/weak-memory behavior.
- Scoped worker launch has a separate `run_services` entry, with the same explicit storage, lifetime, join and unsafe concurrent-native-code obligations. No dynamic CreateThread/StartThread, waits, scheduler, priorities, clocks, actual PAC/FP profile or SDK TLS construction is supplied.

## Validation and measured compiler evidence

Eight new Rust tests (one exhaustive decoder test, one packet-builder unit test and six native integration tests) join all unchanged checks. Native fixtures compile at O0/O2 with fatal UBSan. They check packet W/X results, exact budgets/PCs, C/Rust v3 size/offsets/terminal status, invalid markers/mixed profiles/foreign frames and contexts, failed output batches, local/peer monitor behavior, nested terminal propagation and scoped v3 workers/owner cleanup.

Twelve cases per optimization match QEMU for Linux close(-1) register transport and exception-return monitor clearing, including unsigned boundaries. The fixture models that Linux operation only; it is not a Horizon syscall oracle. Independent native expectations also check every comparison case. Required release tests are additive.

`cpu-survey-services-v3` verifies the supplied ExeFS identities and uses the same indexed extents/CFG/object limits. It conditionally lowers and compiles **143 additional objects**: the existing 64 exclusive-profile extents plus **79 SVC wrappers** (72 SDK, seven rtld). The explicit compiler total is **214,664**. V1/v2 totals remain 214,585; the default strict baseline remains **214,521, gain zero**. No handler mapping, target configuration, runnable-function count or original execution is established by these objects. Generated source/objects, input identities and detailed analysis remain private.
