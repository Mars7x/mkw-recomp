## Concrete dependencies and portability work

**nxnative loading/services.** `dm/host/entry.S` is AArch64; loader.c uses Mach-O/CommonCrypto, native TLS registers and host pointers. Keep our verified NSO/MOD0 loader, dependency-scoped relocation plan and explicit address mapping. Port HLE call selection rather than the loader. Thread/TLS code assumes particular guest TLR/thread-object sizes and a native ARM64 calling context, with Mach/QoS details in host threading. Establish the Switch 2 TLR, thread object, scheduler/wait and memory-order contracts before making those handlers runnable. Some generic service paths return success with zero outputs (`hle_sf.c`), and `hle_sdk16.c` reports a Switch 1 platform; neither is acceptable evidence for our target or suitable as a success stub.

**Files/saves.** Five exact filesystem symbol names have ten supplied binding records across main/SDK with an SDK provider. That is demonstrated API/metadata overlap, not proof of an eight-byte Switch 2 FileHandle or equivalent object ABI. The selected read-only profile therefore stays opt-in. Upstream save work uses APFS/Mach facilities including clone/rename/dirty-page behavior; a Linux save backend needs separately specified transactional/crash semantics and target layouts. No writes, saves, fake MountRom, directory enumeration or general fsp-srv IPC are implemented here.

**LAS portable CPU/Linux.** Makefile explicitly supports Linux x86-64/AArch64, SDL3 and Vulkan; generated x86 code targets x86-64-v3/AVX2/FMA. Required dependencies include Clang, SDL3, Vulkan/shaderc, VMA and FFmpeg with build-dependent licensing. Its Cpu layout and raw-pointer LD/ST macros differ from our owned checked memory; its exclusive fallback is not our shared monitor. `tools/lifter.py` erases PACIASP/AUTIASP as hints and `runtime/simd.h` explicitly omits cumulative FPSR/QC behavior. Importing that CPU wholesale would discard tested semantics. Portable algorithms may be compared behind our existing oracle tests instead.

**Graphics.** LAS's Vulkan device/platform scaffolding is already Linux-oriented. Its `runtime/nvn/maxwell/translate.c` explicitly decodes Maxwell SM5.x instruction groups. nxnative uses a Ryujinx-derived Maxwell shader path with SPIR-V/SPIRV-Cross to Metal. nx2android supplies a Vulkan backend, but builds for aarch64-linux-android, reserves x18 and retains ARM64 entry code; it couples guest pools to AHardwareBuffer/dma-buf/MAP_FIXED and Android surfaces/JNI/AAudio. Linux requires a surface/device backend and a defined staging/import/coherence model, not substitution of an Android handle type. Its Vulkan timeline/replay/resource algorithms remain candidates.

The supplied SDK references NVN bootstrap plus Ounce/native-window V2, native-image and external-memory API families. No inspected upstream implementation establishes the required Switch 2 ABI for those families. We have not established the supplied game's shader instruction format. A small private shader/API identity probe should precede any large renderer transplant; a host Vulkan triangle would only prove the host platform, not a game frame. Full input/graphics runtime compatibility remains unverified.

**Licenses.** The implemented Rust filesystem port is a derivative adaptation, not a clean-room claim. `third_party/nxnative/` retains the actual MIT notices for seedds and the credited d2r-mobile ancestor, source pin/hashes and a change record. No upstream game patches/profiles, shader payloads or generated game code were copied. Its only added direct crate dependency is already-locked libc 0.2.191 (MIT OR Apache-2.0). Potential graphics adoption needs per-component notices: Ryujinx and VMA/ImGui have separate licenses, shader/tool dependencies and FFmpeg build configuration require their own review. The root repository license labels do not cover every bundled component; nx2android's README alone is insufficient provenance for an arbitrary copied file.

## Implemented bounded integration and evidence

- Explicit host-service targets share the coherent CPU-v10/table-v2 call router, checked guest memory and reservation authority. Unknown targets/services fail closed, caller budget/return/base contracts remain checked, and host work has independent byte/handle limits. No raw guest-to-host pointer cast is introduced.
- Five nxnative-derived read-only APIs: OpenFile, counted ReadFile, exact ReadFile, GetFileSize and CloseFile. Linux fd-relative O_NOFOLLOW traversal, regular-file checks, explicit mount, opaque namespaced non-reused handles and read/handle quotas replace upstream host-pointer handles. Guest output batches validate before any writes; successful same-value writes invalidate exclusive reservations.
- Checked hook descriptors require the existing applied relocation plan, exact zero-addend symbol binding, exported function identity, executable entry range and complete five-symbol profile. They neither rewrite relocations nor accept new game extents. Provider hashes/addresses and input-derived details stay private. Binding these descriptors is an explicit opt-in SDK profile, not target authorization.
- Six native call-routing tests, four filesystem tests and two metadata tests pass. Synthetic generated-native fixtures use O0/O2 with fatal UBSan; native/QEMU comparisons cover the CPU call/exclusive sequences. Filesystem semantics additionally compare independent host reads and exercise EOF/partial reads, traversal/symlinks, stale/foreign handles, bad arguments, budgets, output fault atomicity and monitor invalidation. QEMU does not serve as an oracle for Horizon service return codes; those are the selected upstream profile.
- `romfs-hle-check base` verifies supplied identities and the existing link plan, binds five actual SDK descriptors covering ten references, then executes only an author-created four-instruction translated wrapper plus Rust HLE. Open/size/read/close returns **1,342 bytes** matching an independent host read; the input remains unchanged. Original SDK/game instructions do not execute. File names, content/hashes, generated C/library and receipt remain private.
- Coverage gain remains **+0 default / +0 beyond v1**, 214,521 strict extents and 214,585 conditional extents. Runtime integration value is demonstrated resource transport, not an invented runnable-function count.

Next: validate actual target configuration and SDK data layouts; bind the supported closure without bypassing structural boundaries; adapt bounded thread/TLS primitives; identify the required NVN2/shader interfaces before selecting renderer source. No existing acceptance rules or required correctness checks have been relaxed.

## Follow-up runtime and shader evidence

The scoped worker adapter in THREADING.md now implements the bounded ownership/launch/join part of priority 2 for synthetic native code. It uses explicit caller-owned TLS/TLR storage and the existing coherent memory/call authority, retaining borrowed library lifetimes through every join. No native ARM64/Mach context machinery or guessed SDK layouts were imported. Dynamic Horizon lifecycle/waits and actual startup configuration remain open.

A private bounded container experiment evaluated selected unmodified `ctl_len`, `check` and `bnsh_shaders` functions from pinned nxnative `dm/gfx/tools/shader_split.py`, after independent range checks. Four existing sampled archive entries contain eight BNSH occurrences; three standalone entries are duplicates. Each occurrence reaches a rejection of the old control section validator. This is evidence against direct reuse of that sampled extraction/control-layout path. It neither establishes ISA incompatibility nor tests a complete shader translator or graphics backend. All samples, hashes, generated/private test artifacts and input-derived details remain private.
